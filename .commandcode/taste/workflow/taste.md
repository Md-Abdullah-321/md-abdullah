# Workflow & process taste

- Keep changes strictly scoped: touch only the exact sections/features named, and never redesign unrelated pages, the global design system, content, or backend behavior as a side effect. The user states this emphatically (extensive "DO NOT change…" lists) even for small tasks like a hero position swap — no redesign, restyle, content edit, dimension, or spacing change beyond what the new arrangement strictly requires. Confidence: 0.95
- When a previously delivered change overreached the original design, prefers a full revert of the changed file back to its original visual structure followed by applying only the newly requested deltas (verified by diffing against the original), rather than layering more edits on top of the unwanted redesign. Confidence: 0.8
- Inspect the actual implementation and existing architecture before changing anything; don't assume the cause of a bug or guess the design system from memory ("the existing implementation is the source of truth"). Confidence: 0.9
- Diagnose and fix root causes rather than masking problems — e.g., don't hide API errors behind generic messages or fake success states; surface the real error in console/server logs while keeping the UI clean. Confidence: 0.85
- Before coding, trace the relevant data flow (frontend → API/backend → database → component) and identify reusable components so changes build on the existing system. Confidence: 0.8
- When delivering a bug fix, wants an explicit summary of root cause, files changed, whether schema changed, any SQL to run, and how the fix was verified. Confidence: 0.7
- For a bug fix report, wants specifics beyond code: where the feature was (or wasn't) implemented, what prevented it from working, whether an environment variable or CSP/security headers were involved, and exactly how loading/behavior was verified. Confidence: 0.8
- For site-observable behavior (analytics/tag loaders, rendered HTML, response headers), verifies against the production build/deployment — serving the built app and fetching the live production URL to inspect raw HTML and headers — not just localhost dev, because external detection tools and crawlers evaluate what production actually serves. Confidence: 0.85
- When production behavior diverges from local code, first rule out that the code was never deployed before changing code or env config: check git state (committed vs uncommitted changes, local vs remote HEAD) and which commit the host builds from (e.g., Vercel builds from the pushed branch); env vars are injected at build/deploy time, so confirm a redeploy happened after an env var was added/renamed. Root causes like "the code was never pushed/committed" come before any implementation or environment diagnosis. Confidence: 0.8
- For presentational/layout changes, verifies against content-length edge cases (very short, medium, very long content) and at desktop/tablet/mobile widths — including no horizontal overflow — before considering it done. For pixel-precise redesigns this means measuring the actual rendered geometry in a real browser at the exact reference viewport(s): element positions/widths, column gaps, H1 line count and wrapping, shared left/right edge alignment — iterating from measured numbers rather than eyeballing screenshots. Confidence: 0.75
- When a requested behavior cannot be implemented reliably without a significant architecture change (e.g., third-party video progress with no public player API), prefers stopping and reporting the limitation over shipping a fragile workaround. Confidence: 0.8
- Verifies analytics/tag instrumentation by inspecting the actual dataLayer output in DevTools (pushed objects with the expected schema), not by UI behavior alone. Confidence: 0.7
- For every code change — including SEO/metadata/config additions, not just bug fixes — expects the standard validation suite to be run before sign-off: `npm run typecheck`, `npm run lint` (no new errors), and a production build (with the canonical production URL set), followed by a report structured as: exact file changed, exact implementation used, validation results, whether the expected output (e.g., the meta tag) appears in rendered HTML, what old references/assets were replaced, and a short list of things the user should manually check (e.g., visual fit on desktop/mobile, favicon caching). Confidence: 0.8
- Integrate user-provided assets (logos, images, icons) as-is: keep their original filename, path, and format and reference them via the framework's standard public-path/metadata conventions — do not convert, resize, rename, or copy the source files unless there is a clear technical reason. Confidence: 0.7
- Cleanup of superseded references is conservative: remove only what is clearly replaced by the new implementation and never delete unrelated assets, files, or components as a side effect. Confidence: 0.65
- Before editing, after inspecting the relevant code, expects a brief statement of which files/components will be modified and why, followed by the implementation. Confidence: 0.6
- When the user requests a full redesign of a section, restructure it to the new composition specified in the brief — do not make small spacing adjustments to the existing design. Confidence: 0.6
- Explicitly requires that before a scoped change is finished, it is verified that no unrelated styling or component changes slipped in (briefs end with "verify that no unrelated styling or component changes were made") — so sign-off should include a diff/scope check confirming only the requested blocks moved and everything else is untouched. Confidence: 0.65
- Prefers modifying an existing component cleanly over rewriting it from scratch; only rewrite when the current implementation genuinely cannot support the requirement. Confidence: 0.65
- For a behavior task that could touch many similar components, prefers to first inventory the existing implementations (which components exist, how they currently interact, what shared provider/analytics abstractions already exist) before designing the change — reuse the existing shared abstraction rather than creating a second implementation. Confidence: 0.85
- When an intricate behavior change proves hard to get right in one pass, works iteratively: re-reads the actual file state, traces timing/ordering of async events (asynchronous player boot, event echoes, mount ordering), writes the design out before editing, and validates behavior in a real running app rather than trusting that types alone prove correctness. Confidence: 0.7
- Verifies multi-provider playback behavior (play/pause/scroll-pause/no-auto-resume, single-video coordination, autoplay preservation) end-to-end in a real browser against the dev server, using the actual DOM state and dev logs rather than assuming correctness from typecheck. Confidence: 0.65
- Prefers delivery with an explicit report: files changed, architecture used, configurable knobs (e.g., the visibility threshold used), how the behavior is enforced, provider-specific limitations, analytics regression status, and typecheck/lint/build results. Confidence: 0.6
