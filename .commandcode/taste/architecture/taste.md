# Architecture & code taste

- Prefers one shared implementation over duplicates: a single rich-text field component used for both create and edit, one shared Markdown renderer for all project content, one testimonial component reused across pages. Confidence: 0.9
- When a shared component must present differently by context (e.g., homepage hero preview vs. project-detail full quote), keep the single component and add an explicit presentation/variant prop (e.g., `variant="hero" | "detail"`) — never duplicate the component or change the underlying data per context. Confidence: 0.85
- Reuse existing components, design tokens, and libraries; avoid introducing new dependencies, parallel animation libraries (e.g., not both GSAP and Motion), or replacement frameworks unless the current implementation fundamentally cannot support the requirement. Confidence: 0.85
- Avoids premature abstraction: keeps small, hero-scoped content (e.g., a one-off credibility/proof strip) inline in the section rather than extracting it into a component unless it is genuinely reused elsewhere — the user explicitly rejects unnecessary abstractions. Confidence: 0.6
- External service identifiers/configuration (e.g., a GTM container ID) should come from environment variables documented in `.env.example`, never hardcoded — deployments control them via env config. Env keys must use the exact name the user specifies (e.g., `GTM_CONTAINER_ID`, not a renamed `NEXT_PUBLIC_*` variant). Prefers such values read server-side (server components / SSR HTML) so they never ship to client bundles; a plain non-`NEXT_PUBLIC_` key is correct for server-only reads, and never read a non-`NEXT_PUBLIC_` key in a client component — it is undefined in the browser. Confidence: 0.8
- Third-party tag-manager/analytics loaders that external tools must detect (e.g., Google's "Test your website" reading raw HTML) belong inline in the server-rendered HTML via the vendor's standard snippet mounted in the root layout — not deferred via `next/script` `afterInteractive`, which injects client-side and leaves the loader invisible to raw-HTML scanners. Confidence: 0.65
- Which renderer is used should be decided by the field's type/architecture (e.g., `field.type === "richtext"` always renders the rich-text editor), not by record state or context (create vs. edit). Confidence: 0.85
- Content-editing commands must produce real semantic structure (actual list syntax/structure), never cosmetic characters or phantom empty nodes, and editors should follow standard text-editing conventions: Enter continues a list, Enter on an empty item exits it, Shift+Enter is a soft line break, Backspace behaves naturally, and undo/redo round-trips. The editor should feel predictable, not fight the user. Confidence: 0.8
- Editor/form fields must not be reinitialized on every state change: avoid uncontrolled/controlled conflicts and never lose cursor position or selection across typing, formatting, or toolbar actions. Confidence: 0.75
- Sanitize all admin/user-controlled content before rendering and block unsafe URLs/protocols; avoid raw `dangerouslySetInnerHTML` with un-sanitized content. Confidence: 0.8
- Keep the backend and database structure stable; prefer fixes at the rendering/application layer and only touch the database when genuinely required (add columns only where genuinely needed, never for content that is static presentation copy). Confidence: 0.85

- Prefers a single centralized, type-safe analytics/dataLayer helper with one source-of-truth event schema (exact event names, consistent parameter naming) over scattering raw `window.dataLayer.push` calls or ad-hoc payloads across components. Confidence: 0.8
- Event/analytics instrumentation must attach via explicit handlers in the actual components using stable semantic identifiers (cta_name, contact_method, destination) — never button text, CSS classes, textContent matching, global click listeners, MutationObservers, or URL-substring hacks. Confidence: 0.85
- Analytics events must be resilient to React lifecycle behavior (Strict Mode double effects, re-renders, client-side navigation): one interaction/view = one event via per-instance ref guards; view events fire only on the real detail page (never for listing cards); video progress fires at milestones (25/50/75) once per session, not continuously; no timeouts or DOM queries for dedupe. Confidence: 0.8
- Never push PII (email addresses, phone/WhatsApp numbers, client names, personal query strings) into analytics/dataLayer — only semantic categories/methods (contact_method: "whatsapp", project_slug). Confidence: 0.85
- When GTM/GA4 is already installed and receiving events, do not add a second analytics implementation (no gtag.js, extra GA scripts, duplicate tags) — extend the existing stack by pushing structured custom events into the existing dataLayer only. Confidence: 0.8
- Keeps client boundaries small: browser-only access (window/document/dataLayer) lives in client effects or tiny "use client" wrapper components; shared helpers guard window-undefined during SSR and never throw; avoids adding "use client" to large components. Confidence: 0.8
- SEO-critical output — sitemap, robots.txt, page metadata, canonical URLs, and JSON-LD — must be server-rendered via framework-native conventions (Next App Router `metadata` exports, `sitemap.ts`/`robots.ts`, server-rendered JSON-LD) so crawlers and validators see it in raw HTML; no client-side sitemap/metadata generation, and never a second competing implementation when a framework-native one already exists — fix/reuse it. Confidence: 0.85
- The canonical production domain must come from a single centralized config (an explicit env var with a production-host fallback such as `VERCEL_PROJECT_PRODUCTION_URL`) that sitemap, robots, canonical, OG, and JSON-LD URLs all resolve through — never hardcode the domain across files, and never let an unset variable silently fall back to `localhost` in production output. Confidence: 0.85
- The public indexable surface should be driven automatically by the CMS publish state: publishing a project through the Admin must make its page appear in the sitemap and be indexable without any manual per-item code or sitemap-file edits, and unpublishing must remove it; sitemap/SEO data generation should stay lightweight (no N+1, graceful fallback when the database is unavailable). Confidence: 0.8
- Site-wide `<head>` metadata additions such as Google Search Console ownership verification go in exactly one place — the root layout's native `Metadata.verification` field (Next App Router) — so the framework emits the tag on every page via layout inheritance; never per-page duplicate tags, never a visible element, and no parallel mechanism when the root metadata object already exists. Non-sensitive, environment-invariant verification tokens are fine inline in that object (env-var indirection is reserved for deployment-controlled secrets/identifiers). Confidence: 0.7
- When rendering images with the framework image component (`next/image`), supplies real intrinsic width/height (or `fill` inside an aspect-ratio parent) to prevent layout shift, preserves aspect ratio, applies object-cover only where cropping is intended, and reserves `priority` for above-the-fold images that actually need it. Confidence: 0.7
- Avoids circular imports between co-located components (e.g., header ↔ mobile menu both needing the shared logo) by extracting the shared piece into its own file rather than leaving a fragile render-time import cycle. Confidence: 0.8
- Uses the site's established motion/duration/easing tokens and existing animation library for all new motion, so interactions feel consistent with the design system. Confidence: 0.75
- Responsive multi-column layouts should be built on CSS grid (with the existing breakpoint system) — never hardcoded absolute pixel positioning per item. Confidence: 0.6
- Centralizes cross-component runtime policy (e.g., "currently playing video" across all videos on the page) in a single lightweight, non-React coordinator with synchronous state rather than duplicating pause/coordination logic inside each component, relying only on React state, or adding a state-management library for it. Confidence: 0.85
- For third-party integrations, prefers a provider-agnostic abstraction: application code talks to a thin controller contract (play/pause/getState/destroy) and never to provider-specific internals, so YouTube/Loom/future providers plug into one interface without the app being hardcoded around a single vendor. Confidence: 0.8
- Never implements behavior by querying or manipulating third-party DOM (`document.querySelectorAll("video")`, `iframe[src*="youtube"]`, poking internal iframe elements). When a provider's public API cannot reliably support a requirement, do not fake it with fragile DOM hacks — document the limitation and integrate only as far as the public API allows. Confidence: 0.85
- Prefers IntersectionObserver for viewport-visibility-driven behavior over attaching scroll listeners to elements (no expensive per-element scroll listeners); visibility signals are used only to pause an item that is already playing once it clearly leaves the viewing area — they never auto-start or auto-resume anything. Confidence: 0.85
- Site-wide media behavior must be one consistent system across every page and provider: videos never autoplay merely by being on the page or entering the viewport (explicit user interaction required; autoplay only where deliberately designed, e.g., the hero), at most one video plays at a time, a playing video pauses when scrolled out of the meaningful viewport (~40% visibility), and a paused video stays paused until the user explicitly clicks play again. Confidence: 0.8
